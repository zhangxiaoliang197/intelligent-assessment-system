# 指标来源标注优化方案

## Context（背景）

"指标分析"功能当前存在一个数据可信度问题：LLM 自行给生成的指标打来源标签（`admin-db` / `knowledge` / `llm`），而非根据实际数据来源标注。这导致两个具体缺陷：

1. **知识库标签被滥用**：指标分析路径（`indicator_analysis`）从未调用 knowledge-service 检索知识库，但 prompt 却要求 LLM "基于知识库中的专业知识"生成指标并标注 `knowledge` 来源。LLM 在无任何知识库数据可查的情况下，用自身训练数据编造指标并打上 `knowledge` 标签，误导用户以为这些指标有知识库依据。
2. **admin-db 标签名不副实**：prompt 注入了 admin-service 已配置指标作为参考，LLM 据此打 `admin-db` 标签，但这些指标并未真正回写到 `ass_indicator` 表，标签含义与实际不符。

对比之下，`concept_qa`（概念问答）路径已正确实现：真正调用 knowledge-service 检索 + admin-service 取指标 + 注入 prompt。

**目标**：不让 LLM 自主打来源标签，改为代码层根据实际证据（是否匹配 admin-service 已配置指标、是否能对应到 knowledge-service 检索结果）标注 `type`/`source` 字段，并同步修改所有受影响的地方。

## 受影响范围（已确认）

### 后端 `python/indicator-service/main.py`
- **L696-748** `analyze_indicator_stream` 主流程的第一次 LLM prompt：让 LLM 自打 `type`/`source`，且不查知识库
- **L778-808** parse 后直接透传 LLM 返回的 `type`/`source`，无校验
- **L819-841** 第二次 LLM 调用（自然语言总结）：拼 `[{ind['type']}]` 且要求 LLM 自己报告"来源分布"
- **L211-271** `call_llm_for_indicator_analysis`（非流式辅助函数）：同样让 LLM 自打标，需同步修复保持一致

### 前端 `frontend/src/pages/IndicatorAnalysis.vue`（无需改动，仅核对一致性）
- L141-142 指标卡片标签（`ind.type`）
- L300 表格标签（`ind.type`）
- L943 tree 节点着色（`node.source === 'knowledge'`）
- L948 tree tooltip（`params.data.source`）

字段名（`ind.type` / `node.source`）和取值范围（`admin-db`/`knowledge`/`llm`）保持不变，前端无需改动。

### 不修改的部分
- `_handle_concept_qa_stream`（L72-167）：已正确实现，不动
- `get_default_tree`（L313-345）、`/indicator/detail`（L929）、`/indicator/list`（L968）：硬编码 `source:"admin-db"` 是正确的（这些接口只从 admin-service 取数），不动
- `parse_structured_response`（L274-310）：用 `.get()` 取值，天然兼容 LLM 不返回 type/source，不动
- Phase 2 路径（`_stream_indicator_query`）：不使用 `type`/`source` 字段，不受影响

## 实施步骤

### 步骤 1：新增来源标注辅助函数（main.py，放在 `parse_structured_response` 之后、`get_default_tree` 之前）

复用 `utils.py` 的 `http_get`/`http_post`，复用 `config.py` 的 `ADMIN_SERVICE_URL`/`KNOWLEDGE_SERVICE_URL`。

**数据获取函数（消除重复，参考 concept_qa 路径 L82-96）：**
- `_fetch_admin_indicators() -> List[Dict]`：从 `ADMIN_SERVICE_URL/api/admin/indicator/list` 拉取已配置指标，失败返回 `[]`
- `_fetch_kb_results(query, top_k=5) -> List[Dict]`：调用 `KNOWLEDGE_SERVICE_URL/knowledge/search` 检索知识库，失败返回 `[]`（与 concept_qa 路径一致）

**文本构建函数（主流程与非流式函数复用）：**
- `_build_admin_indicators_text(admin_indicators) -> str`：拼成 `## 系统中已配置的指标` 段落，并提示"如能复用请保持名称完全一致以便系统识别"
- `_build_kb_text(kb_results) -> str`：拼成 `## 知识库检索到的相关参考资料` 段落

**来源匹配函数（核心算法，匹配优先级 admin-db > knowledge > llm）：**
- `_normalize_name(name) -> str`：去空格/标点/转小写（中文友好）
- `_char_bigrams(text) -> set`：2-gram 字符集合（与 knowledge-service 的 TF-IDF 风格一致，不引入 jieba）
- `_match_admin_indicator(ind_name, admin_indicators) -> Optional[Dict]`：三档匹配 —— ①归一化名称完全相等 ②包含关系（短串长度≥2）③2-gram Jaccard ≥ 0.6
- `_match_kb_result(ind_name, ind_definition, kb_results) -> Optional[Dict]`：两档匹配 —— ①指标名（长度≥2）出现在 chunk 的 title+content 中 ②definition 的 2-gram 与 content 的 2-gram Jaccard ≥ 0.5
- `_annotate_indicators(indicators, admin_indicators, kb_results) -> List[Dict]`：给每个 indicator 写入 `type` 字段（admin-db / knowledge / llm）
- `_annotate_tree_source(tree, indicators) -> Optional[Dict]`：根据指标 type 构建 name→type 映射，递归标注 tree 叶子节点 source；中间/根节点取子节点中最高优先级来源（admin-db=3 > knowledge=2 > llm=1）
- `_compute_source_distribution(indicators) -> Dict[str, int]`：返回 `{'admin-db': N, 'knowledge': M, 'llm': K}`

### 步骤 2：修改 `analyze_indicator_stream` 主流程（main.py L696-748）

- 用 `_fetch_admin_indicators()` + `_fetch_kb_results(request.query)` 替换原 L698-714 的内联拉取
- 用 `_build_admin_indicators_text()` + `_build_kb_text()` 构建注入文本
- **重写 prompt**：
  - 删除"基于 1)数据库 2)知识库 3)自身知识"指令
  - 删除"来源标注规则"段（L743-746）
  - JSON 格式中 **移除 `type`/`source` 字段**，显式声明"不要在 JSON 中输出 type 或 source 字段，来源标签由系统根据实际数据来源自动标注"
  - 保留"如能复用已配置指标请保持名称完全一致"的引导（便于代码层匹配）

### 步骤 3：在 parse 后添加代码层标注（main.py L778-808 之间）

在 `result = parse_structured_response(full_text)` 之后、`set_pending_indicators` 之前插入：
```python
indicators = _annotate_indicators(indicators, admin_indicators, kb_results)
tree = _annotate_tree_source(tree, indicators)
source_dist = _compute_source_distribution(indicators)
```
并加 debug 日志便于核对实际分布。

### 步骤 4：修改第二次 LLM 调用 prompt（main.py L819-841）

- `ind_brief_parts` 不再拼接 `[{ind['type']}]`（避免把标签喂给 LLM 让它复述）
- 用 `_compute_source_distribution` 的结果生成 `dist_text`（如"admin-db(已配置)1 个，knowledge(知识库)0 个，llm(AI生成)4 个"）
- prompt 中把"包含来源分布（admin-db/knowledge/llm 各多少）"改为"以下是由系统精确统计的来源分布数据，请直接引用，不要自行估算：{dist_text}"

### 步骤 5：同步修复 `call_llm_for_indicator_analysis`（main.py L211-271）

- 用相同的 `_fetch_*` + `_build_*` 函数构建 prompt
- prompt 移除 `type`/`source` 字段要求
- parse 后调用 `_annotate_indicators` + `_annotate_tree_source`

### 步骤 6：前端核对（无代码改动）

确认 `IndicatorAnalysis.vue` 四处引用的字段名和取值范围与后端输出一致（已在背景章节核对完毕），无需改动。
