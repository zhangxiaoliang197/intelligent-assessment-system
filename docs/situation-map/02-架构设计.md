## 2. situation-service 设计

### 2.1 职责边界
- **唯一拥有者**：态势图的生成编排、流式推送、产物聚合、跨功能草稿态。
- **不做**：不持有本体/向量库；不直连 MySQL（持久化经 admin-service）；不实现地图渲染（前端同事负责）。

### 2.2 模块结构（建议）

```
python/situation-service/
├─ main.py                 # FastAPI 入口, 路由聚合
├─ config.py               # 端口/超时/调参常量 (os.getenv)
├─ logging_config.py       # 复用项目统一日志 (与各服务同构)
├─ llm_client.py           # 自带 LLM 客户端 (照 ontology-service 模式, 扩展 tool_calls)
├─ agent/
│  ├─ orchestrator.py      # tool-calling 主循环
│  ├─ tools.py             # 工具定义 + 派发 (调下游服务)
│  └─ prompts.py           # system prompt + 工具 schema
├─ stream/
│  ├─ sse.py               # SSE 事件流封装
│  └─ events.py            # 事件类型定义 (plan/dataset/chart/map_layer/narrative/...)
├─ store/
│  ├─ admin_client.py      # 调 admin-service CRUD (持久化/列表/分享)
│  └─ draft.py             # 草稿态内存/缓存 (带 TTL)
├─ datasources/
│  ├─ knowledge.py         # 调 qa/knowledge
│  ├─ indicator.py         # 调 indicator
│  ├─ evaluation.py        # 调 qa(evaluation)
│  ├─ admin_data.py        # 调 admin 数据源/指标
│  └─ external.py          # 外部实时数据源适配器 (预留, 可插拔)
└─ models.py               # Pydantic 数据模型 (Report/Chart/Layer/Narrative/Draft)
```

### 2.3 服务结构约定（对齐现有 Python 服务）
- FastAPI 应用，`title`/`description` 用中文。
- `setup_logging("situation-service")` 统一日志，`LOG_ENV` / `LOG_LEVEL` / `LOG_DIR` 环境变量驱动。
- CORSMiddleware 允许跨域（与 ontology-service 同）。
- 所有下游服务 URL 走 `os.getenv`，默认 `http://localhost:10xxx`，**不硬编码**（见 08 章环境变量表）。
- 响应统一 `{success, message, data}`。
- 跨服务调用加超时（建议 5–30s）+ 异常捕获 + 降级。

### 2.4 LLM 客户端（关键扩展）
复用 [ontology-service/llm_client.py](../../python/ontology-service/llm_client.py) 模式：
- `load_llm_config()`：从 `ADMIN_SERVICE_URL/api/admin/config/llm/active` 取活跃配置，三级兜底（active → list → 硬编码默认）。
- `call_llm(messages, ...)`：OpenAI 兼容 `/chat/completions`，urllib + 跳过自签名证书校验。
- `call_llm_json(messages, ...)`：带容错重试的 JSON 解析。

**新增扩展**（situation-service 独有）：
- `call_llm_with_tools(messages, tools, tool_choice="auto")`：在请求体加 `tools` 字段，返回原始响应（含 `tool_calls`）。用于 agent 循环。
- 若目标模型不支持 function-calling，降级为「JSON 计划模式」：`call_llm_json` 产出 `{plan: {datasets, charts, map_layers}}`，由编排器执行（见 03 章 Q-01）。

## 3. 跨服务调用关系

| 调用方 → 被调方 | 用途 | 环境变量 | 默认值 |
|------------------|------|----------|--------|
| situation → admin | LLM 配置 / 地图配置 / 持久化 CRUD / 数据源指标 | `ADMIN_SERVICE_URL` | http://localhost:10258 |
| situation → qa | 知识检索 / 评估结果 | `QA_SERVICE_URL` | http://localhost:10253 |
| situation → knowledge | 知识库直接检索（可选） | `KNOWLEDGE_SERVICE_URL` | http://localhost:10252 |
| situation → indicator | 指标数据 | `INDICATOR_SERVICE_URL` | http://localhost:10254 |
| situation → external | 外部实时数据源（预留） | `EXTERNAL_DS_URL`（多个） | 空 |

> **独立于本体**：默认不调用 ontology-service，不配置 `ONTOLOGY_SERVICE_URL`，体现「独立于本体模型」约束（ADR-01/05）。

## 6. 与现有模块的关系

| 现有模块 | 关系 |
|----------|------|
| 知识问答 (qa-service) | 被态势图作为数据源工具调用；也可作为跳转来源 |
| 指标分析 (indicator-service) | 被作为数据源工具调用；也可作为跳转来源 |
| 评估分析 (经 qa-service) | 被作为数据源工具调用；也可作为跳转来源 |
| 本体模型 (ontology-service) | **无依赖**（独立） |
| 向量库 (Qdrant) | **无依赖**（独立；knowledge-service 可作为工具间接用到，但态势图自身不持有） |
| admin-service | 提供 LLM 配置、地图配置、持久化 CRUD |

## 7. 关键设计权衡

- **为何新建服务而非复用 qa-service**：qa-service 承载问答/评估/附件等重逻辑，态势图需独立演进（实时推送、外部数据源、产物持久化），耦合会互相拖累（ADR-02）。
- **为何持久化经 admin-service 而非自带 DB**：admin-service 是现有数据管控入口，DB 表结构统一管理，避免 Python 服务散落直连 DB（ADR-11）。
- **为何 SSE 而非 WebSocket**：生成阶段为单向推送（server→client），SSE 经 nginx 代理更简单（`proxy_buffering off`）；若后续需双向交互（用户在生成中调整筛选）可再升级 WS（ADR-07）。
- **为何地图用最深耦合（共享状态）**：用户要求地图与图表同源且联动，共享 Pinia 状态最直接（ADR-04/ADR-13）。
